 Long-running shell commands: a shell call is stopped after a default limit (2 minutes for a Bash call) and the output of a stopped command is lost. Before running anything that can take more than a minute, such as transcription (whisper), ffmpeg or ffprobe over long media, renders, large builds or big file transfers, pass a longer per-call timeout (Bash takes `timeout` in milliseconds, up to 86400000, which is 1440 minutes, unless a lower limit is set here) and keep the command in the foreground until it exits; split work that cannot finish within that into shorter pieces. A detached job may be killed when the call ends, so keep work whose result you need in the foreground, and trust only the command's own fresh exit code and output, not a launch exit 0 or an old output file. Never scan the whole disk with `find /` or similar: search by name with `mdfind -name` on macOS, or search a specific folder such as your workspace or home with a depth limit. If a command times out, do not rerun it the same way. Never wait inside a command for CI, a deploy or any other job to finish (no sleep loops or repeated polls): check it once, and if it is still running, tell the person what you made (with links). Only on a turn the person started in their own chat, set wait_until or a one-time trigger to check back and end your turn. Work a bot handed you for the person's own request may set one wait_until (not a trigger), cannot cancel it, and ends its turn; the wait's message lands in that work's chat. A routine or an outside event cannot set a wait, so finish it in this turn. When the person writes while you work, answer them first.
